# Comparison V4 Experimental Methodology

## 1. What the Experiment Tested

This experiment compared three ways to obtain a smaller or faster neural chess
evaluation model:

1. **Knowledge distillation:** train a smaller student to imitate a larger
   neural teacher while also learning from Stockfish-generated labels.
2. **Dynamic INT8 quantization:** replace FP32 linear-layer computations and
   weights with dynamically quantized INT8 equivalents for CPU inference.
3. **Unstructured magnitude pruning:** set a specified fraction of linear
   weights to zero, then fine-tune the model for one epoch.

Stockfish itself was not quantized or pruned. Stockfish 18 was the external
expert used to create the original move and position-value labels. The
experiment first trained an FP32 neural **Stockfish surrogate**, which is called
the teacher in the comparison. Quantization and pruning were then applied to
that trainable surrogate and to the distilled student.

The primary question was not simply whether a model contained fewer useful
weights. It was whether each method improved the practical tradeoff among:

- agreement with Stockfish's preferred move;
- serialized model size on disk;
- one-thread, batch-one CPU inference latency.

## 2. Data and Stockfish Labels

The experiment reused 74,731 labeled chess positions. These labels had already
been generated by analyzing positions with:

- Stockfish 18;
- search depth 10;
- MultiPV 5.

Each JSONL row contained:

- the position in FEN notation;
- a `game_id`;
- Stockfish's five highest-ranked moves;
- a centipawn evaluation for each move.

An example has this general form:

```json
{
  "fen": "...",
  "labels": [
    {"move": "e2e4", "eval_cp": 33},
    {"move": "g1f3", "eval_cp": 27}
  ],
  "game_id": "676"
}
```

### Game-grouped split

The split was performed by `game_id`, not by independently shuffling
positions. All positions from one game therefore remained in one split:

| Split | Positions | Games |
|---|---:|---:|
| Training | 59,760 | 1,780 |
| Validation | 7,496 | 234 |
| Test | 7,475 | 220 |

The runner loaded the three files and explicitly intersected their `game_id`
sets. It aborted if any overlap was found. The recorded train/validation,
train/test, and validation/test overlaps were all zero.

The validation split was used for early stopping and hyperparameter selection.
The test split was used only after model selection for final metrics.

## 3. Position and Target Encoding

### Board input

Each position was encoded as 18 binary `8 x 8` planes:

- 12 piece planes, one for each piece type and color;
- one side-to-move plane;
- four castling-right planes;
- one en-passant plane.

The tensor therefore contained `18 x 8 x 8 = 1,152` input features after
flattening.

### Move representation

The policy output contained 20,480 possible action indices:

```text
64 source squares x 64 destination squares x 5 promotion states
```

Only legal moves were considered during policy loss calculation and move
ranking. Illegal action logits were effectively set to negative infinity.

### Stockfish policy target

The five MultiPV centipawn scores were converted into a probability
distribution:

```text
perspective = +1 for White to move, -1 for Black to move
adjusted_score_i = perspective * eval_cp_i
target_probability_i = softmax(adjusted_score_i / 80)
```

The perspective correction is important because Stockfish centipawn values in
the dataset use White's perspective, while move desirability must use the
perspective of the player whose turn it is.

### Value target

The value target used the best listed move's White-perspective centipawn score:

```text
value_target = tanh(best_eval_cp / 1000)
```

This bounded the regression target to approximately `[-1, 1]`. Unlike the
policy target, it intentionally remained White-perspective.

## 4. Teacher and Student Models

Both models were multilayer perceptrons with a shared trunk and separate policy
and value heads.

### FP32 surrogate teacher

```text
1,152 inputs
-> Linear(1,152, 1,024) + ReLU
-> Linear(1,024, 512) + ReLU
-> policy head: Linear(512, 20,480)
-> value head: Linear(512, 1) + tanh
```

The teacher contained approximately 12.21 million parameters.

### Student

```text
1,152 inputs
-> Linear(1,152, 256) + ReLU
-> Linear(256, 128) + ReLU
-> policy head: Linear(128, 20,480)
-> value head: Linear(128, 1) + tanh
```

The student contained approximately 2.97 million parameters.

These are dense feed-forward networks, despite older project documents using
the phrase "student CNN." The final comparison used the MLP architectures
listed above.

## 5. Training Design

Eight independent random seeds were used:

```text
7, 17, 27, 37, 47, 57, 67, 77
```

For each seed, the runner trained:

- one independently initialized FP32 surrogate teacher;
- one directly trained student;
- nine distilled students from a `3 x 3` hyperparameter grid.

The direct and distilled students within a seed started from the same initial
student weights. This reduced initialization as a source of variation when
comparing direct training with distillation.

### Optimization

- optimizer: AdamW;
- learning rate: `3e-4`;
- weight decay: `1e-4`;
- batch size: 256;
- maximum epochs: 20;
- early-stopping patience: four epochs;
- mixed-precision training on CUDA;
- best checkpoint selected by validation objective.

Training stopped when validation loss failed to improve by at least `1e-5` for
four consecutive epochs. The best validation checkpoint, rather than the final
epoch, was restored.

### Direct teacher and student loss

The teacher and direct student minimized:

```text
L_stockfish = L_policy + L_value
```

where:

```text
L_policy = soft cross-entropy against the Stockfish MultiPV distribution
L_value  = MSE(predicted value, Stockfish value target)
```

Both terms had weight 1.

### Distillation loss

The distilled student learned from both the original Stockfish targets and the
FP32 surrogate teacher:

```text
L_total = (1 - alpha) * L_stockfish + alpha * L_teacher
```

The teacher component was:

```text
L_teacher =
    temperature^2 * KL(teacher policy || student policy)
    + MSE(teacher value, student value)
```

The policy distributions were restricted to legal moves. The
`temperature^2` factor compensated for gradient scaling introduced by
temperature softening.

The tested grid was:

```text
alpha:       0.25, 0.50, 0.75
temperature: 1.0, 2.0, 4.0
```

The configuration with the lowest mean validation Stockfish policy
cross-entropy across all eight seeds was selected:

```text
alpha = 0.50
temperature = 2.0
```

No test metric was used for this choice.

## 6. Compression Conditions

Thirteen conditions were evaluated for every seed:

1. FP32 teacher.
2. Direct FP32 student.
3. Distilled FP32 student.
4. Dynamically quantized INT8 teacher.
5. Unpruned teacher fine-tuning control.
6. Teacher pruned to 25%.
7. Teacher pruned to 50%.
8. Teacher pruned to 75%.
9. Dynamically quantized distilled student.
10. Unpruned distilled-student fine-tuning control.
11. Distilled student pruned to 25%.
12. Distilled student pruned to 50%.
13. Distilled student pruned to 75%.

This produced `13 x 8 = 104` held-out condition evaluations.

### Dynamic INT8 quantization

PyTorch dynamic quantization was applied to every `nn.Linear` layer:

```python
torch.ao.quantization.quantize_dynamic(
    model.cpu().eval(),
    {nn.Linear},
    dtype=torch.qint8,
)
```

Dynamic quantization stores linear weights in INT8 and determines activation
quantization scales during inference. It is primarily a CPU optimization.

The quantized model was saved, reloaded on CPU, and then evaluated. Reloading
verified that the reported model was a usable serialized artifact rather than
only an in-memory transformation.

### Unstructured pruning

Pruning used global unstructured L1 magnitude pruning across the weights of all
linear layers. "Global" means weights from all eligible layers were ranked
together, and the smallest absolute values were removed until the requested
overall sparsity was reached.

For each sparsity level:

1. copy the unpruned base model;
2. apply a 25%, 50%, or 75% binary pruning mask;
3. fine-tune for one epoch at learning rate `1e-4`;
4. keep the pruning mask active during fine-tuning;
5. remove PyTorch's pruning reparameterization;
6. save and evaluate the resulting dense tensor containing explicit zeros.

An unpruned control received the same extra fine-tuning epoch and optimizer
settings. This separated effects caused by pruning from effects caused merely
by additional training.

## 7. Held-Out Accuracy and Value Metrics

Every selected condition was evaluated on all 7,475 test positions.

### Top-1 agreement

```text
top1 = positions where model's highest-ranked legal move
       equals Stockfish's first MultiPV move
       / total test positions
```

### Top-3 agreement

Top-3 counted a success if Stockfish's first MultiPV move appeared anywhere in
the model's three highest-ranked legal moves.

### Other metrics

- policy cross-entropy against the Stockfish MultiPV distribution;
- value mean squared error;
- value RMSE, calculated as `sqrt(value MSE)`;
- Pearson correlation between predicted and target values.

These metrics measure imitation of Stockfish labels. They are not direct
measurements of chess Elo or game-playing strength.

## 8. Exact CPU Latency Calculation

CPU latency was measured by
`measure_latency_ms()` and `latency_distribution()` in the experiment scripts.

### What was timed

The benchmark timed only the model's forward pass. It did not include:

- reading FEN or JSONL data;
- converting a chess board into an input tensor;
- DataLoader overhead;
- model loading from disk;
- move decoding;
- batching multiple positions.

Therefore, the result represents neural-network inference cost for an already
encoded position.

### Input and execution settings

- device: CPU;
- batch size: one position;
- sample: the first encoded position in the held-out test set;
- PyTorch CPU threads: one;
- model mode: `eval()`;
- gradient tracking: disabled.

The same position shape and benchmark procedure were used for every condition.

### One latency trial

For one trial, the script:

1. saved the current PyTorch thread count;
2. set `torch.set_num_threads(1)`;
3. moved the model and one-position sample to CPU;
4. ran 20 untimed warm-up forward passes;
5. started `time.perf_counter()`;
6. ran 300 consecutive forward passes;
7. stopped the timer;
8. restored the previous thread count.

The trial latency was:

```text
trial_latency_ms =
    (ending_time - starting_time) * 1000 / 300
```

Warm-up reduced first-call initialization and cache effects. Dividing one timer
interval by 300 also reduced timer-resolution noise.

### Repeated trials and seeds

The complete trial was repeated seven times for each model in each seed.

For one seed-condition pair:

```text
seed latency = median(seven trial means)
```

The seven raw trial values and their 25th and 75th percentiles were retained in
`per_seed_metrics.csv`.

For the final aggregate:

```text
reported CPU latency = median(eight seed latencies)
```

The final latency error bars were the 25th and 75th percentiles of those eight
per-seed medians. They are therefore latency interquartile ranges, not 95%
confidence intervals.

As an example, the FP32 teacher aggregate latency was approximately `2.324 ms`
per position, while the INT8 teacher was approximately `0.496 ms`:

```text
speedup = 2.324 / 0.496 = approximately 4.7x
```

## 9. Exact Storage Calculation

The main storage metric was the number of bytes in the serialized PyTorch file
actually written to disk:

```text
serialized_size_MiB = file_size_bytes / (1024 * 1024)
```

Although the plots say MB for readability, the calculation technically uses
mebibytes because it divides by `1024^2`.

### FP32 teacher and students

Training checkpoints were saved as a dictionary containing:

- model kind;
- `state_dict`;
- training metadata.

The runner measured the resulting checkpoint file with
`Path.stat().st_size`.

### Quantized models

Quantized PyTorch modules contain packed quantization objects, so the complete
model object was serialized with `torch.save(model, path)`. Its actual file
size was then measured.

### Pruned models

After pruning reparameterization was removed, the pruned model's
`state_dict()` was serialized and measured.

The zero-valued FP32 weights were still present in dense tensors. Consequently,
unstructured pruning did not materially reduce the actual serialized size:

```text
FP32 teacher:       approximately 46.59 MiB
75% pruned teacher: approximately 46.59 MiB
```

This is expected. Setting weights to zero is not the same as storing a sparse
matrix.

### Size reduction shown in the table

Every displayed size reduction was relative to the mean FP32 teacher file
size:

```text
size_reduction_percent =
    100 * (teacher_size - model_size) / teacher_size
```

For the INT8 teacher:

```text
100 * (46.59 - 11.72) / 46.59 = approximately 74.9%
```

### Theoretical sparse payload

The script also calculated a diagnostic sparse-storage estimate for pruned
models. It assumed a COO-like representation containing:

- one FP32 value per nonzero weight: 4 bytes;
- one INT32 flat index per nonzero weight: 4 bytes;
- normal dense storage for non-pruned parameters.

This estimate was:

```text
sparse_weight_bytes = nonzero_weights * (4 + 4)
```

It was not used as the main poster storage result because no such sparse file
or sparse inference implementation was actually produced.

### Storage-comparison caveat

The measured artifacts are all real PyTorch files, but their serialization
containers are not perfectly identical:

- trained FP32 checkpoints include a state dictionary plus metadata;
- pruned files contain a state dictionary;
- quantized files contain the full packed model object.

Weights dominate these files, so the main conclusions are robust, but the
numbers should be described as **actual serialized artifact sizes**, not as a
byte-perfect controlled comparison of one universal file format.

## 10. Aggregation and Uncertainty

For accuracy and most model metrics, the script calculated the arithmetic mean
across the eight seeds.

The plotted 95% interval was:

```text
CI95 = 1.96 * sample_standard_deviation / sqrt(8)
```

The sample standard deviation used `n - 1` in the denominator. This is a
normal-approximation confidence interval across random seeds.

CPU latency was treated differently because timing distributions can be
skewed. It used medians and interquartile ranges, as described above.

Paired accuracy differences were also computed within each random seed. For
example:

```text
delta_seed = teacher_INT8_top1_seed - teacher_FP32_top1_seed
```

The mean and confidence interval of these paired differences more directly
measure compression effects than comparing two independent-looking error
bars.

## 11. How the Poster Graphs Were Produced

### Compression-method comparison

The aligned panels show:

- mean test top-1 agreement;
- mean serialized artifact size;
- median CPU latency.

The displayed methods are the FP32 teacher, INT8 teacher, direct student,
distilled student, and validation-selected combined student condition.

### Accuracy versus CPU inference cost

For each condition:

- x-coordinate: median CPU latency across seed medians;
- y-coordinate: mean test top-1 agreement across seeds;
- horizontal error bar: latency interquartile range;
- vertical error bar: approximate 95% confidence interval across seeds.

A condition was placed on the Pareto frontier if no other condition was both:

- at least as accurate; and
- at least as fast;

with a strict improvement in at least one dimension.

The frontier is descriptive. It does not account for uncertainty when deciding
whether one point dominates another.

## 14. Interpretation Boundaries

The experiment supports these conclusions:

- dynamic INT8 quantization produced a real reduction in serialized size and
  CPU latency with almost no average change in move agreement;
- the smaller students were substantially smaller and faster than the FP32
  surrogate;
- distillation was competitive with direct training but not conclusively
  superior across seeds;
- ordinary dense PyTorch execution did not turn unstructured zeros into
  meaningful storage or latency savings.

The experiment does not establish:

- that the Stockfish executable itself was compressed;
- that top-1 move agreement is equivalent to playing strength;
- that the models would have the same latency on different CPUs;
- that pruning cannot help when paired with sparse serialization, structured
  pruning, or hardware-aware sparse kernels.
